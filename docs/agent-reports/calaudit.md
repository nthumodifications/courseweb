Reproduction snippets below were run against the checked-in `calendar_utils.tsx` with `TZ=Asia/Taipei` unless noted.
Statuses below describe source-level paths; no browser acceptance run was performed, so a source path marked implemented is not a claim of verified production behavior.

## 2. Repeat/recurrence correctness

### Expansion and end conditions

- **bug — `apps/web/src/components/Calendar/calendar_utils.tsx:118-140`**: date-mode termination compares the occurrence’s full local timestamp to `new Date(event.repeat.value)`. The form stores a selected end date as local midnight (`EventForm.tsx:680-687`), so an event at 09:00 on the selected final date is treated as later than the end and omitted. Reproduction: daily event `2026-09-10 09:00–10:00`, mode `date`, value `new Date(2026, 8, 12).getTime()` returns Sep 10 and Sep 11 only, not Sep 12. Smallest fix: compare local calendar dates, or normalize the repeat-until date to end-of-day in the recurrence model.
- **bug — `apps/web/src/components/Calendar/EventForm.tsx:558-568` and `eventFormSchema.tsx:7-10,18-46`**: the form validates event end > event start but does not validate a date-mode repeat end on/after the event start. A user can choose a repeat end before the event; the expander still always yields the base occurrence (`calendar_utils.tsx:118-121`). Smallest fix: add a cross-field refinement for repeat date >= start’s calendar date and reject malformed stored rules as well.
- **bug — `apps/web/src/components/Calendar/calendar_utils.tsx:118-140`**: expansion starts from the event’s original start and generates every occurrence up to the rule end before filtering against the requested view. A large count/far-future date can block rendering and the view does not bound the work. Smallest fix: calculate the first occurrence at or before the requested range and stop at the range end, while retaining the rule’s count/date limit.

### Month/year arithmetic and actual end

- **bug — `apps/web/src/components/Calendar/calendar_utils.tsx:90-100,118-140`**: `addMonths` is applied repeatedly to the previous result, so a Jan 31 monthly event becomes Feb 28, then Mar 28. Confirmed reproduction: Jan 31 2026 monthly/count 3 returns Jan 31, Feb 28, Mar 28. Smallest fix: anchor each occurrence to the original year/month index and define an explicit policy for invalid month days (usually clamp to the last day or skip).
- **bug — `apps/web/src/components/Calendar/calendar_utils.tsx:194-204`**: yearly rules have the same leap-day drift: repeated `addYears` from Feb 29 becomes Feb 28 permanently. Smallest fix: anchor to the original month/day and define Feb 29 behavior.
- **bug — `apps/web/src/components/Calendar/calendar_utils.tsx:173-191`**: weekly date-mode `getDisplayEndDate` can calculate an end after the requested repeat date. For a Monday event ending 10:00 and a Sunday cutoff, `diff = Sunday(0) - Monday(1)`, then `addDays(cutoff, -diff)` returns the following Monday. Confirmed reproduction returns Sep 21 for a Sep 20 cutoff. Smallest fix: calculate the last occurrence by stepping backward from the cutoff to the event weekday and clamp it to the cutoff.
- **gap — `apps/web/src/components/Calendar/calendar.types.ts:26-28`, `calendar_utils.tsx:146-207`**: `actualEnd` is described as the recurrence bound, persisted on every write (`calendar_hook.tsx:224-231`), but the display path never reads it; display always recomputes from the mutable rule. Smallest fix: either remove the dead field or make one tested recurrence-bound function use it consistently for rendering, server querying, and ICS.

### Exceptions, delete-this, and edit-this

- **verified behavior — `apps/web/src/components/Calendar/calendar_hook.tsx:238-253`**: delete-this appends `operationEvent.displayStart` to `excludedDates`; `eventsToDisplay` checks `isSameDay` against it (`calendar_utils.tsx:57,72`). This is date-based rather than occurrence-ID-based, which is important for the timezone and DST defects below.
- Source-level edit-this behavior is implemented by excluding the root occurrence and inserting a detached child with `repeat: null` and `parentId` set to the root (`apps/web/src/components/Calendar/calendar_hook.tsx:306-330`). It was not browser-verified and inherits the date-based exception and schema-contract risks called out below.
- **bug — `apps/web/src/components/Calendar/calendar_hook.tsx:255-270`**: delete-following changes `repeat.value` to a millisecond timestamp but preserves the prior mode. For a count rule, that timestamp is interpreted as a count, and `getActualEndDate` can attempt to add roughly 1.7 trillion intervals and fail before the update. Reproduction: five daily occurrences, delete from occurrence three; the code constructs `mode: "count", value: subDays(...).getTime()`. Smallest fix: set `mode: "date"` when writing a date timestamp, or subtract the remaining count and retain count mode.
- **bug — `apps/web/src/components/Calendar/calendar_hook.tsx:306-330,381-389`**: edit-all uses the edited occurrence’s `displayStart/displayEnd` because `EventPopover` passes them as the form’s `start/end` (`EventPopover.tsx:181-188`). The root series is therefore re-anchored to whichever occurrence was clicked, losing all earlier occurrences. Smallest fix: for `ALL`, preserve the root event’s anchor (`oldEvent.start/end`) and apply only series-wide fields/time deltas; use occurrence dates only for `THIS`/`FOLLOWING`.
- **bug — `apps/web/src/components/Calendar/EventForm.tsx:261-295`**: when editing an existing repeated event, switching Repeat to “No Repeat” clears interval/mode/value, then switching directly to another repeat type does not restore defaults because `defaultEvent.repeat` remains truthy. The resulting daily/weekly rule lacks required fields and cannot save. Smallest fix: initialize missing interval/mode/value whenever a non-null type is selected, not only when the original event was non-repeating.
- **gap — `apps/web/src/components/Calendar/calendar_hook.tsx:272-277`**: deleting “all” only removes the selected event ID and children whose `parentId` equals that ID. If the selected event is a detached repeated child, its original root and sibling branch remain. Smallest fix: resolve the root ancestor before applying `ALL`, then delete the entire root/child family.
- **bug — `services/secure-api/src/utils/icalendar.ts:99-110`**: personal ICS export maps `repeat.value` to `until` for every rule. In count mode `value` is an occurrence count, so `new Date(10)` is a 1970 date instead of an end condition; the ICS has no `COUNT` equivalent. Smallest fix: emit `COUNT` for count mode and `UNTIL` only for date mode, with date-only/timezone tests.
- **bug — `services/secure-api/src/utils/icalendar.ts:43-64`**: the personal ICS query filters on the base event `start`/`end`, not `actualEnd`. A recurring series whose first occurrence is in the past but whose recurrence continues is excluded before ICS generation. Smallest fix: query recurring records by `actualEnd` (or a recurrence-aware index) and keep the overlap predicate consistent with the web expander.

### DST and cross-midnight behavior

- **bug — `apps/web/src/components/Calendar/calendar_utils.tsx:39-46`**: recurrence dates are advanced with local calendar arithmetic, but the end is rebuilt by adding the original millisecond duration. For a 01:30–03:30 event on Mar 7 2026 in `America/New_York`, the next start is Mar 8 01:30 EST while the rebuilt end is Mar 8 04:30 EDT; a wall-clock recurrence would normally end at 03:30. Asia/Taipei itself has no DST, but the source has no timezone contract and can run in a DST-observing browser. Smallest fix: choose and document wall-clock-vs-instant semantics, then use timezone-aware calendar arithmetic for both start and end.
- **bug — `apps/web/src/components/Calendar/calendar_utils.tsx:68-83`, `CalendarWeekContainer.tsx:159-204`**: non-all-day events are included only when `displayStart` lies inside the day. A 23:30–01:00 event is not rendered on the following day even though the week renderer contains code intended to cap cross-midnight end times. Smallest fix: include any interval intersecting the day (`displayEnd >= dayStart && displayStart <= dayEnd`) and clip both ends for the day column.

## 3. Timezone handling

The web code has no explicit `Asia/Taipei` timezone. It constructs and formats JavaScript `Date` values in the browser’s local timezone, then persists instants as UTC ISO strings. The server-side course ICS is explicit about Taipei, but the personal-event web calendar is not consistently explicit.

### Exact local/UTC boundaries

|---|---|---|

## 4. Data durability

### What is stored and what is actually synced

The local database is a Dexie-backed RxDB named `nthumods-calendar`; the events collection is schema version 1 (`apps/web/src/config/rxdb.tsx:18-104,146-171`). The current source is not strictly browser-only: authenticated `useCalendarProvider` starts live event replication to secure-api (`apps/web/src/components/Calendar/calendar_hook.tsx:67-128`), and secure-api implements `/api/replication/events/pull` and `/events/push` into `users/{userId}/events` in Firestore (`services/secure-api/src/api/replication.ts:37-262`). I did not verify that deployed route, auth scope, Firestore rules, or replication completion, so server durability is implemented-but-unverified rather than confirmed production behavior.

| Action | Current source-level result |
|---|---|
| Clear site data / IndexedDB | Local events and RxDB replication checkpoints disappear. If the authenticated event replication path is live and the token has the `calendar` scope, a subsequent sign-in can pull the server copy; anonymous or unsynced events are lost. If the path is unavailable, all local-only events are lost. |
| Use a second device | There is no user-facing event export/import. Authenticated events can be pulled from the secure-api/Firestore replication path; local-only/anonymous events cannot. This is not live-verified. |
| Switch browsers | Same as second device: same-account replicated events may return; local-only events do not. |
| Log out with “keep local data” checked | The events collection remains (`apps/web/src/components/Header.tsx:51-80`). A second account in the same browser can see the unscoped local collection because `useCalendarProvider` queries all events and the database name/collection is not user-keyed (`calendar_hook.tsx:64,204-220`). Smallest fix: namespace local DB/collection by user or clear/isolate events on identity change. |
| Log out with “keep local data” unchecked | The events and timetable-sync collections are removed locally (`Header.tsx:58-80`); a server copy, if replication succeeded, is not revoked/deleted by logout. |

- **bug/security gap — `apps/web/src/components/Calendar/calendar_hook.tsx:64,204-220` and `apps/web/src/components/Header.tsx:53-80`**: events are not keyed by authenticated user, while local data is retained by default. Reusing a browser profile across accounts can expose the previous account’s events and may mix replication state. Smallest fix: put the user ID in the DB/replication identity and clear or isolate on logout/login.
- **gap — `apps/web/src/components/Calendar/calendar_hook.tsx:67-128`**: replication errors only go to `console.error`; the UI does not tell the user that a local write is not durable. Smallest fix: expose replication status/error and provide an export/retry affordance.
- **gap — `apps/web/src/components/Calendar/calendar_hook.tsx:67-70` and `services/secure-api/src/middleware/requireAuth.ts:42-67`**: the client starts event replication for any authenticated user, but secure-api requires the `calendar` scope. A scope-less token fails with 403 and the local write continues. Smallest fix: gate replication on the actual scope and surface the unsynced state.

### Export and migration path

- The course timetable ICS path is an export/subscribe path, but it does not include personal RxDB events (`TimetableBottomBar.tsx:17-28`, `services/api/src/timetable-ics.ts:301-331`).
- The personal ICS share path reads server Firestore events, not the local database directly (`services/secure-api/src/utils/icalendar.ts:43-75`). There is no app UI matching `/calendar/share-tokens` (`services/secure-api/src/api/calendar.ts:27-120`); only the backend contract exists.
- **bug — `apps/web/src/config/rxdb.tsx:19-20,169-273`**: the only migration strategy is key `1`, for the current version. If the schema changes to version 2, no version-2 strategy exists. The current strategy also defaults `excludedDates`, `parentId`, and `details`, but not required `actualEnd`, `color`, or `tag` (`rxdb.tsx:191-224,243-249`); old documents missing any of those required fields can still fail validation. Smallest fix: add a tested strategy for every new version and backfill every newly required property, including `courseId` if it is added.

## 5. Timetable and calendar coupling

### Current sync flow

1. `Calendar.tsx` iterates the locally selected course IDs by semester and reads one `timetablesync` document per semester (`Calendar.tsx:262-289`).
2. It converts the current courses to `CourseTimeslotData`, but compares only `course.raw_id` sets, not times, venue, color, or title (`Calendar.tsx:290-307`).
3. The dialog reports “new” or “modified” and, on acceptance, converts each course slot to a weekly event anchored at semester start and ending at semester end (`CalendarTimetableSyncDialog.tsx:41-56`, `timetableToCalendarEvent.tsx:11-57`).
4. It inserts/upserts the new generated events and records the new course-ID set/checkpoint (`Calendar.tsx:320-345`). Rejected changes are also recorded as seen, so the same prompt is not shown again for that set.

- **bug — `apps/web/src/components/Calendar/Calendar.tsx:320-345`**: accepted sync calls async `addEvent` through `calendarEvents.forEach(...)` without awaiting the returned promises, then writes the sync checkpoint. A failed or still-pending event upsert can therefore be hidden by a checkpoint that says the course set was handled. Smallest fix: `await Promise.all(calendarEvents.map(addEvent))` before saving the checkpoint and surface failures.

### Course add/drop and semester behavior

- **bug — `apps/web/src/components/Calendar/Calendar.tsx:290-307,324-343`**: dropping a course produces a “modified” request but acceptance only adds current courses; it never removes old events for the dropped course. Smallest fix: identify generated events by `courseId`/semester and delete or reconcile removed IDs in the same transaction-like operation.
- **bug — `apps/web/src/components/Calendar/Calendar.tsx:290-307`**: changing a course’s time, venue, or other timetable fields without changing its raw ID is not detected, so stale generated events remain. Smallest fix: compare a stable hash of all generated slot fields, or reconcile all generated events for the semester on acceptance.
- **bug — `apps/web/src/components/Calendar/Calendar.tsx:262-269`**: if all courses are removed, `Object.keys(courses).length === 0` returns before reconciliation, leaving old course events. Smallest fix: allow an empty current set to reconcile previously synced semesters.
- **bug — `apps/web/src/components/Calendar/Calendar.tsx:271-307`**: semesters that disappear from `courses` are never visited, so their old events are not actively removed. Their recurrence may naturally end at the old semester, but the stale records remain. Smallest fix: compare stored synced semester keys against current keys and clean generated events for removed semesters.
- **bug — `apps/web/src/components/Calendar/timetableToCalendarEvent.tsx:20-29`**: it force-unwraps `semesterInfo.find(...)`. A new semester not yet added to `packages/shared/src/constants/semester.ts` crashes sync rather than reporting an unavailable semester. Smallest fix: return a typed error/empty result and keep the semester table as one shared source of truth.
- **gap — `apps/web/src/components/Calendar/timetableToCalendarEvent.tsx:34-57` and `apps/web/src/config/rxdb.tsx:19-98`**: generated events carry `courseId`, but `courseId` is absent from the RxDB schema properties. RxDB normalizes schemas to `additionalProperties: false` (verified in the installed RxDB helper), so dev validation can reject these generated documents; production validation behavior was not live-tested. Smallest fix: add `courseId` as an optional schema property and include it in the typed document/migration before relying on course-date annotations.
- **gap — `apps/web/src/components/Calendar/Calendar.tsx:369-379`**: other-timetable overlays are rendered only in week view and are not persisted/synced as calendar events. This is consistent with an overlay, but the UI does not communicate that month/upcoming views omit it. Smallest fix: either render overlays in all views or label the feature as week-only.

### Custom user-defined timetable time blocks

The current calendar converter accepts only `CourseTimeslotData`, whose `startTime/endTime` are numeric indexes into the fixed `scheduleTimeSlots` array (`apps/web/src/types/timetable.ts:20-28`, `apps/web/src/helpers/timetable.ts:39-84`). To render custom blocks precisely:

## 9. Performance

- **bug — `apps/web/src/components/Calendar/calendar_utils.tsx:28-87,118-140`**: every view expands every event and every recurrence from its original start to its final rule bound before range filtering. - **bug — `apps/web/src/components/Calendar/CalendarWeekContainer.tsx:159-193`**: each day calls `eventsToDisplay`, then layout computes `concurrent` by filtering all day events for every event, making overlap layout O(events²) per day. - **bug — `apps/web/src/components/Calendar/CalendarMonthContainer.tsx:91-135,178-210,240-275`**: month rendering repeats event expansion for each cell, then filters all-day events for each event and each cell. - **gap — `apps/web/src/components/Calendar/Calendar.tsx:369-379`**: timetable overlays are converted with `flatMap(timetableToCalendarEvent(...))` inline during every render rather than memoized. Smallest fix: `useMemo` by overlays/language/custom-slot data.
